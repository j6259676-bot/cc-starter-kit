# dev-workflow — 做大東西的流程模組

給任何要交給 AI 做「一次講不完的東西」的夥伴：一個報名頁、一份課程大綱、一個查詢工具、一場活動的完整流程。**不限程式開發** — 只要是預估超過半小時、做錯了要重來的產出，這套都適用。

## 這個模組在解決什麼

新手用 AI 最貴的失敗長這樣：講一句話，AI 洋洋灑灑做出一大坨東西，你看完覺得「不是我要的」，但已經分不清哪裡開始歪掉，只好整個重來。

原因幾乎都不是 AI 不夠聰明，而是**還沒共識就開工**。這套流程把「做」拆成五步，每一步都有一個你點頭的關口：

| 步驟 | 指令 | 你在這一步做什麼 |
|---|---|---|
| 1. 拷問 | `/brainstorm` | 回答它一題一題的問題，直到你自己也想清楚了 |
| 2. 規格 | `/spec` | 看它整理的規格對不對，特別是「你要在哪裡驗收」 |
| 3. 切片 | `/plan` | 看它怎麼把事情切成一片一片，順序對不對 |
| 4. 實作 | `/build` | 一片一片驗收，每片都要看到證據 |
| 5. 檢查 | `/review` | 看它自己抓出的問題，決定要不要修 |

**核心一句話：共識前不動工，一片驗收完才做下一片。**

## 什麼時候不要用這套

不要用在：寫一封信、改個錯字、回答一個問題、整理一份現成資料。這些直接講就好，套流程只是折磨自己。

判準：**你講得完的事情，直接做；你講不完的事情，走流程。**

還有一個例外：你自己也還不知道要什麼，只是想探索 — 那就只用第 1 步（`/brainstorm`），聊完得到一段共識摘要就結束，不用往下走。

## 安裝步驟（Claude 照做）

### 1. 安裝指令

把本模組 `commands/` 底下的五個檔案複製到使用者專案的 `.claude/commands/`（沒有這個資料夾就建立）：

```bash
mkdir -p .claude/commands
cp modules/dev-workflow/commands/*.md .claude/commands/
```

裝好後在 Claude Code 裡輸入 `/` 就會看到 `brainstorm`、`spec`、`plan`、`build`、`review` 五個指令。

### 2. 合併規則

把 [CLAUDE-snippet.md](CLAUDE-snippet.md) 的內容加進使用者的 CLAUDE.md（先給使用者看過再改）。重點是那條「口語提出新東西時自動進入流程」— 使用者不需要記得打指令。

### 3. 帶跑一次

問使用者：「你最近有沒有想做但還沒開始的東西？」挑一個真的、小的（一個報名表、一份流程文件、一個小工具），從 `/brainstorm` 開始完整跑一次到第 4 步交出第一片。

跑的時候刻意示範兩件事：

- **拷問階段一次只問一題，而且每題都附上你的建議答案。** 讓使用者體會「原來我不用自己想，我只要說對不對」
- **第一片交出來時附上證據**（打開網址、跑出結果），讓使用者知道「完成」長什麼樣子

## 日常用法

使用者不用背指令。他口語說「我想做一個 XX」的時候，AI 就該主動說：「這件事看起來要做一陣子，我先問你幾個問題把它釐清好嗎？」然後進入流程。

他隨時可以問「我們現在在流程的哪一步？」來檢查有沒有脫軌。

## 用在非程式的事情上

五個步驟原封不動，只是名詞換一下：

| 程式開發 | 換成別的事情 |
|---|---|
| 規格（SPEC.md） | 企劃書、活動 brief、課程大綱 |
| 切片（每片可 demo） | 每一段可以單獨拿給人看的成果（第一天的教材、報名頁的其中一區） |
| 完成證據 | 檔案打得開、內容對照需求逐條檢查過 |
| `/review` 的 Standards 軸 | 換成「對照我過去的寫作範例，語氣像不像我」 |
| `/review` 的 Spec 軸 | 不變 — 對照規格逐條檢查漏做、多做、做錯 |

`/review` 的 12 個程式碼壞味道表對非程式產出用不到，跳過就好，Spec 軸才是重點。

## 心法

這套流程的來源是「先立靶再開槍」：**開工前就講好完成時你會看到什麼**，而不是做完才回頭找證據。所有失控的專案都是從「我以為我們講的是同一件事」開始的。
