---

在我們對計畫達成共識之前，針對每個面向往深處問。沿著決策樹走，一次解開一個決策之間的依賴。

目的：把決策權留在我手上，你負責找出我還沒想清楚的盲點。

## 規則

- **一次只問一題**，等我回答再問下一題。一次丟五題會讓人放棄回答，只挑最好答的答
- **每題附上你的建議答案**，含理由。白話優先、少術語（假設我不是工程師）。我大部分時候只需要說「對」或「不對，應該是 X」
- **事實與決策分開**：能靠查資料得到的事實（檔案內容、線上網址、既有資料長什麼樣、某個工具支不支援），**自己去查，不要問我**。只有需要我拍板的決策才問
- **共識達成前不寫任何程式碼、不建任何檔案**，不管任務看起來多簡單

## 該問什麼（決策樹順序）

1. **目的與對象** — 這東西是給誰用的？他們在什麼情境下用？不做會怎樣？
2. **成功長什麼樣** — 做完之後，你會在哪裡看到它、怎麼判斷它是對的？
3. **範圍邊界** — 哪些是這次一定要有的、哪些是「有更好但這次不做」？
4. **既有的東西** — 現在是怎麼處理的？有沒有已經存在的資料、表單、檔案要接？
5. **限制** — 時間、帳號權限、誰要維護、資料能不能對外？

問到我開始重複同樣的答案、或說「就這樣」，就是共識了。

## 順手建立語彙

過程中出現有歧義的術語（我們兩個理解可能不同的詞，例如「會友」「報名」「完成」），當場確認定義，寫進這個專案資料夾的 `CONTEXT.md`。

原則：**第一個歧義詞出現時才建檔**，不要預先寫一份詞彙表。每條三行：

```markdown
**新朋友**
第一次參加聚會、還沒進小組的人。以報名表單的「第一次參加」欄位為準。
_避免_：「慕道友」（那是另一個階段）、「新人」（太模糊）
```

## 出口

我說「可以了」「就這樣做」＝共識達成。

- 要做出東西 → 進 `/spec` 寫規格
- 純討論、不做東西 → 用一段共識摘要收尾，並問我要不要把結論寫進記憶
