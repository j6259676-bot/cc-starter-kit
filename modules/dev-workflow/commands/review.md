對這次的改動跑**兩軸檢查**。兩軸**分開報告、不要合併排名** — 一軸全過會遮住另一軸的問題。

---

## 第一軸：品質（Standards）

先看這個專案既有的慣例，再用下面的基線。每一條都是判斷題不是硬性違規；專案已經寫清楚的慣例可以蓋過基線；工具（lint）已經在管的跳過。

| 壞味道 | 症狀 → 修法 |
|---|---|
| 名字看不懂 | 名字看不出用途 → 改名。想不出一個誠實的名字，通常代表設計有問題 |
| 重複的程式碼 | 同樣形狀的邏輯出現在多個地方 → 抽成共用 |
| 眼紅別人的資料 | 一個函式碰別人的資料比碰自己的多 → 把它搬到資料那一邊 |
| 資料成群結隊 | 同一組欄位總是一起出現 → 打包成一個型別 |
| 迷戀原始型別 | 用字串／數字硬扛領域概念 → 給那個概念自己的小型別 |
| 重複的分支判斷 | 同一種型別的 if/switch 串在多處重複 → 收斂成一個地方 |
| 散彈式修改 | 改一件事要動好幾個檔案 → 把它們聚攏到一個模組 |
| 一檔多變因 | 一個檔案因為好幾個不相關的理由被改 → 拆開 |
| 為未來預留的抽象 | 為了不存在的需求加彈性 → 刪掉，等真需求出現 |
| 一長串點點點 | `a.b().c().d()` → 讓第一個物件包一個方法藏住細節 |
| 只會轉手的中間人 | 一個類／函式只是把呼叫轉給別人 → 砍掉直接呼叫 |
| 繼承了卻不用 | 繼承來的東西大多用不到或被覆寫 → 改成組合 |

**非程式產出**（文案、教材、企劃）跳過這張表，改成對照 `200_Reference/writing-samples/` 檢查：語氣像不像我、有沒有用到我禁用的詞、格式跟過去的一致嗎。

## 第二軸：規格對照（Spec）

拿 SPEC.md（沒有規格就拿原始需求）逐條比對，找三類問題：

- **漏做或只做一半** — 規格寫了但東西裡沒有
- **沒被要求的行為** — 東西裡有但規格沒寫（順手加的功能也算，這是範圍膨脹）
- **看起來做了但做錯** — 名字對、位置對，行為跟規格描述的不一樣

每一條發現都要**引用規格原文**，讓我能自己判斷是規格寫錯還是做錯。

---

## 輸出格式

```
## 品質軸
- [重要] 檔案:行號 — 問題描述 → 建議修法
- [建議] ...
（一行總結）

## 規格對照軸
- [重要] 規格第 3 段寫「報名後寄確認信」，目前沒有寄 → ...
（一行總結）
```

嚴重度分三級：**嚴重**（會出錯／會外洩／會弄壞資料）、**重要**（該修但不急）、**建議**（可做可不做）。

## 加跑的情況

改動涉及網頁對外、登入權限、金鑰或成員個資 → 額外檢查一遍：有沒有把金鑰寫進檔案、有沒有讓不該看到的人看到資料、使用者輸入的東西有沒有直接塞進網頁或查詢語句。
